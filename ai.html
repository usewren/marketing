How it works

Three ways in. All of them safe.

One server, one MCP endpoint. What you publish, anyone’s agent can find and use. What you keep private, only your agents reach — with your permissions, and nothing they do is permanent.

Public data, no key

Any agent can connect to /mcp without signing up, see who publishes what, and read published sites and collections. Always the released version, never your drafts.

Private data, as you

“Sign in with WREN” from Claude, Cursor or VS Code, pick the org, and the agent works with your groups’ access. Or give it an API key. Revoke either at any time.

Safe to let it write

Agent writes land as new versions labeled preview. Review the diff, promote what’s good, roll back what isn’t. Nothing is overwritten.

Features

What your agents work with.

Versioned collections and sites your team already uses — the same data, the same permissions, for people and agents.

Tenant isolation

Each org gets its own Postgres schema. An agent signed in to one org can’t see another — isolation is structural, not a policy to misconfigure.

Deploy, preview, promote

wren deploy to a preview, check it, then promote the whole site in one transaction. Roll back the same way.

Work together

Invite people by email straight into groups like Editors or Viewers. Admins can view the org as a member to help — and every change made that way is recorded as such.

How it works

Three primitives. One API.

Each one is useful on its own — together they replace a week of plumbing.

1

Collections hold your data

POST any JSON object. Schema-free by default, or attach a JSON Schema when you’re ready to lock it down. Binary uploads are first-class.

2

Versions remember everything

Every write creates a version. Diff, roll back, or pin a label to serve a specific snapshot to your clients.

3

Trees give you structure

Organize documents into a named hierarchy. Fetch a single path, bundle a subtree, or expose the whole thing as public URLs.

API Reference

A handful of endpoints. Documents, versions, trees.

The full API is documented at /docs. Here’s the shape of it.

bash 
# Create a document
curl -X POST /api/v1/events \
  -d '{"name": "Masters 2026"}'

# Update (creates version 2)
curl -X PUT /api/v1/events/abc \
  -d '{"name": "Masters 2026", "champion": "Scheffler"}'

# Pin a label
curl -X POST /api/v1/events/abc/labels \
  -d '{"label": "published"}'

# Attach to a tree path
curl -X PUT /api/v1/tree/site/2026/masters \
  -d '{"documentId": "abc"}'

# Bundle the published snapshot of the whole site tree
curl /api/v1/tree/site?full=true&label=published

Client Libraries

First-class TypeScript & Python clients.

Documents, versions, labels, trees. Full types. Zero extra dependencies. Works in Node, Bun, and async Python.

TypeScript & JavaScript npm install @usewren/client 
import { WrenClient } from "@usewren/client";

const wren = new WrenClient({ baseUrl, apiKey });

// Documents
const doc = await wren.documents.create("events", data);

// Versions & labels
const hist = await wren.versions.list("events", doc.id);
await wren.labels.set("events", doc.id, "published");

// Trees
await wren.trees.set("site", "/2026/masters", doc.id);
const bundle = await wren.trees.getFull("site");
